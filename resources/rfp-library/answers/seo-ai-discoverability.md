# SEO & AI discoverability

Source: validated RFP submission, 2026-07-30. Trust: `validated`.

The honest position: the CMS covers meta/OG natively; canonical, hreflang,
JSON-LD, sitemaps and redirects are **front-end implementation patterns**.
Say so plainly — but always name the delivery route on the prospect's
actual target stack, because "requires custom development" alone reads as
a gap when it's really framework-native work.

| Requirement | Answer | Route |
|---|---|---|
| Meta title/description, OG, per page + per locale | Supported OOTB | Native SEO app |
| Canonical + hreflang | Supported with configuration | Next.js Metadata API (`generateMetadata`) — standard, documented, framework-native |
| Structured data (JSON-LD) | Requires custom development | Front-end generated from the structured content fields |
| SSR/SSG for indexable pages | Supported OOTB | API-first + framework-agnostic; SSR/SSG/ISR is first-class |
| Redirect management for non-developers | Requires custom development | CMS story as redirect data store, queried via API — **plus** on Vercel, native redirect config + Edge Config with a dashboard non-developers can use. Present the combination. |
| XML sitemaps per locale | Requires custom development | `next-sitemap` or a script against the Links API |

## Native SEO/quality tooling worth naming
- **Broken Links Checker** — a native app that scans and resolves broken
  links across every story in a space. The right answer to "regular scanning
  of redirects and 404s / don't waste crawl budget", and easy to miss because
  it isn't part of the SEO app. **Gate: Premium/Elite** per the official fact
  sheet's Apps table (an earlier note here said Growth Plus+, and a search
  snippet claimed Growth Plus — the fact sheet is the better source; verify
  on the live page if it's decision-relevant). Setup needs an admin to issue
  a preview token.
- **Field-level required validation** in content types — covers
  "enforceable rules before publication" (mandatory meta fields etc.).
  Heading structure (a single H1) stays authoring/template discipline; the
  CMS doesn't enforce it.

## Core Web Vitals levers that ARE platform-side
Most CWV requirements are honestly frontend responsibilities, but two are
genuinely Storyblok's and worth claiming rather than deferring:
- The **Image Service enforces width/height via URL parameters**, directly
  preventing image-driven layout shift (CLS).
- The **component schema can carry a `fetchpriority` field**, letting
  editors mark the hero/LCP element high priority.
Everything else (reserving space for dynamic injects, `font-display`,
below-the-fold lazy loading, preconnect hints, code-splitting/minification)
is frontend build work — say so plainly, then name these two.

## AI / LLM discoverability
Content is stored and delivered as structured, typed JSON — directly
consumable by LLMs and AI crawlers without HTML stripping. Plus a hosted
MCP Server for programmatic/agentic access, and semantic content
intelligence on the roadmap. Note that final rendered HTML quality still
depends on the front-end implementation; don't over-claim.

## Added from the 2026-09-15 architecture RFI (`validated`)

### The full element-by-element table (more precise than the grid above)
| Element | Position | Where implemented |
|---|---|---|
| Metadata (title/description, OG, Twitter Card) | **Native** — SEO app adds a `seo-metatags` field type with a Google-snippet preview. **AI SEO app** adds an `sb-ai-seo` field generating the same tags from page content, **across 26 languages** | Field data in the CMS; rendering into `<meta>` in the template |
| Structured data (JSON-LD) | ⚠️ **No automatic generation.** Content is modelled with fields mapping to Schema.org types (Organization, LocalBusiness per location, etc.) | JSON-LD serialisation in the render layer |
| **Canonicals** | ⚠️ **No dedicated canonical-URL field ships with the base SEO app.** Add a `canonical_url` field to the schema — a standard text field, no extra cost | Frontend renders `<link rel="canonical">`, falling back to the current URL when empty |
| **Robots directives** | ⚠️ **Not in the base SEO app fields** — no noindex/nofollow toggle. Add a `robots` field via the same custom-field pattern as canonicals | Frontend renders `<meta name="robots">` or `X-Robots-Tag` |
| Redirects | ⚠️ **No native redirect execution engine** — we are not the serving frontend or the router. Pattern: a dedicated "Redirects" content type/datasource (from-path, to-path, status code) with full CRUD, versioning and workflow | We store and govern the mapping; their CDN/compute issues the actual 301/302 |
| Sitemaps | ⚠️ **No native generation.** Query the CDA for published stories (slugs, `updated_at`, locale) to assemble `sitemap.xml` | Generated by the app at build or request time |
| hreflang | ⚠️ Not auto-generated — per-locale slug/language list and alternates supplied via the API | Rendered by the app |

**Be careful with the canonical and robots rows specifically** — the earlier
note in this file implied canonical was covered by the SEO app. It is not;
it is a custom field. The precise answer is "a standard text field on the
schema, no extra platform cost, rendered by the frontend."

### GEO / llms.txt — the buildable-pattern answer
All content is delivered as **structured JSON, machine-readable at source**.
A markdown/`llms.txt` output for LLMs is achievable **the same way
`sitemap.xml` already is in this architecture** — the frontend generates it
from the same structured JSON, and can include FAQ-formatted content not
otherwise surfaced on the live site. Call it **a real, buildable pattern,
not a native one-click feature**, and say the same of JSON-LD. Then
separate out the **first-party hosted MCP server** (OAuth or token auth),
which lets AI tooling query and act on content directly — *that* one **is
native**, not a frontend pattern.

Holding that line — "these two are patterns, this one is native" — is more
persuasive than claiming the whole GEO section, and it is the shape the
validated answer used.

### The migration risk that outweighs the SEO fields
Volunteer this in any replatform: **the bigger SEO risk sits outside the
metadata fields.** Any URL change from the legacy platform needs a **301
redirect map built from the legacy sitemap and server logs, loaded into the
redirects content type**. Tie it to the prospect's own seasonal peak if they
have one — protecting existing organic rankings through the transition is a
business risk, not a content-fields exercise, and framing it that way is
what makes the answer read as consultative.
